0. Revue critique & évolution v1.0 → v2.0

Cette section recense les anomalies relevées dans la conception v1.0 et les décisions retenues en v2.0. Elle sert de journal de décisions techniques pour l'équipe.

0.1 Corrections (bugs de conception)

Réf.Problème v1.0Décision v2.0
FIX-1 montant_unit déclaré COMPUTED : impossible en PostgreSQL, une colonne générée ne peut dépendre d'une agrégation (Σ coefficients) portant sur d'autres lignes. Calcul porté dans le service CalculFacture ; persistance dans facture_locataire.montant_du. Aucune colonne générée inter-lignes.
FIX-2 nb_personnes saisi à la main et redondant avec Σ coefficients. La v1.0 ne précise jamais quels locataires sont rattachés à une facture. Table de liaison facture_locataire = source de vérité. nb_personnes devient dérivé (count) et non saisi. Sélection explicite des locataires concernés (ou « tous les actifs »).
FIX-3 Table paiements absente du modèle alors que POST /api/paiements et le workflow l'invoquent. Pas de mode, ni référence, ni paiement partiel. Table paiements dédiée (montant, mode, référence MoMo/OM, encaisseur, justificatif). Paiements partiels supportés ; statut recalculé.
FIX-4 DECIMAL(12,2) pour des montants en XAF : le franc CFA n'a pas de subdivision en usage. Montants en entiers : BIGINT (XAF). Les coefficients restent DECIMAL(4,2).
FIX-5 Contradiction « eau / électricité » dans la prédiction : la formule I·P+TVA+LC+T est propre à l'électricité. Module de prédiction paramétré par type de charge (électricité, eau…), chaque type ayant sa formule. Renommé « estimation » (déterministe, pas du ML).
FIX-6 Audit trail cité en §9 mais absent du modèle de données. Table audit_logs formalisée + middleware d'audit sur toutes les actions sensibles.

0.2 Risques de conception revus

Risque sécurité — Signal de détresse

La désactivation automatique du bouton après « 3 signaux en 3 jours » s'applique à une fonction de sécurité vitale. Bloquer un résident réellement en danger plusieurs jours d'affilée est inacceptable et engage la responsabilité de la cité. v2.0 : on remplace le blocage dur par (a) un anti-abus progressif (throttle + cooldown), (b) une mise en revue admin au lieu d'une coupure, (c) la possibilité pour l'admin de lever toute restriction instantanément. Le ban manuel admin reste possible mais journalisé.

Mot de passe ≥ 4 caractères

Avec un login = simple username, 4 caractères exposent à du bruteforce trivial. v2.0 : minimum 8 caractères (la 1re connexion impose le changement), rate-limit strict, verrouillage temporaire, et 2FA TOTP optionnel pour l'Admin. Le « 4 caractères » initial n'est toléré que pour le mot de passe temporaire généré, jamais conservé.

Reconduction automatique des factures

Reconduire en silence peut propager un montant erroné indéfiniment. v2.0 : la reconduction crée un brouillon is_reconducted=true non publié, notifie l'admin pour validation, et un compteur reconduction_streak déclenche une alerte au-delà de 2 mois consécutifs.

0.3 Adaptations au contexte camerounais (ajouts v2.0)

  • + Mobile Money Enregistrement natif des paiements Orange Money / MTN MoMo (mode + référence + capture). Intégration API en option (phase 2).
  • + SMS Canal SMS (passerelle locale type Nexah/Twilio) pour les rappels d'échéance et signaux de détresse — plus fiable que l'email localement.
  • + Offline-first Stratégie PWA renforcée pour connexion intermittente et data coûteuse : cache agressif, compression d'images, file de synchronisation différée.
  • + Compteurs Modélisation des chambres / blocs / compteurs pour répartir eau & électricité par compteur physique.
  • ? Allemand Les langues officielles sont FR/EN. Le DE est conservé (architecture i18n prête) mais marqué optionnel : à confirmer selon le public réel, vu le coût de traduction/maintenance.

1. Introduction & objectifs

1.1 Contexte

CampusGest est une Progressive Web App (PWA) de gestion complète d'une cité universitaire au Cameroun. Elle digitalise et centralise les interactions entre l'Administration, le Bailleur et les Locataires : facturation et paiements, communication, vie communautaire et suivi financier. L'objectif d'usage est une ouverture quotidienne par chaque résident, soutenue par les notifications push et SMS.

1.3 Périmètre & contraintes

  • Seul l'administrateur est créé au déploiement (seed idempotent). Tout autre compte est créé via l'interface Admin.
  • Le mot de passe temporaire généré doit être changé dès la première connexion ; le mot de passe permanent fait ≥ 8 caractères.
  • Les coefficients sont saisis mensuellement ; à défaut, n = 1 pour tous.
  • En l'absence de nouvelle facture pour un type donné, un brouillon reconduit du mois précédent est proposé à l'admin (jamais publié automatiquement).
  • Les abus de signal de détresse passent en revue admin (jamais de coupure silencieuse de la sécurité).
  • Montants en XAF entiers. Devise et formats respectent la locale de chaque utilisateur.

4. Rôles & authentification

4.1 Flux d'authentification

  1. L'Admin se connecte avec les credentials seedés (mot de passe initial à usage unique, changement forcé).
  2. L'Admin crée les comptes Bailleur/Locataire ; un mot de passe temporaire est généré et transmis hors-bande (SMS/remise).
  3. À la 1re connexion → redirection vers « Changer mes identifiants » (nouveau mot de passe ≥ 8 caractères).
  4. Hash bcrypt (salt rounds = 12).
  5. Login réussi → access token JWT HS256 (15 min) + refresh token (7 j, cookie HttpOnly/SameSite=Strict).
  6. Payload access : { sub, role, ver, iat, exp } (ver = compteur d'invalidation pour révocation).
  7. Middleware centralisé : vérification signature/exp, puis roleGuard par endpoint.
  8. 2FA TOTP optionnel pour l'Admin (étape supplémentaire post-mot de passe).
Durcissement vs v1.0

Access court (15 min) + refresh rotatif > le JWT 24h de la v1.0 : limite la fenêtre de compromission. Révocation via users.token_version.

5. Modules fonctionnels

5.1 Facturation & coefficients

Cœur financier. L'Admin crée des factures mensuelles par type, rattache les locataires concernés, attribue des coefficients et fixe l'échéance.

Répartition :
base_unitaire = montant_total / Σ(coefficients des locataires rattachés)
montant_du(i) = round(base_unitaire × coefficient(i))   (écart d'arrondi reporté sur la dernière ligne)

Exemple — Eau = 60 000 XAF, 4 locataires (coeff 1, 1, 0.5, 1.5) → Σ = 4.0 → base = 15 000
A(1)=15 000 · B(1)=15 000 · C(0.5)=7 500 · D(1.5)=22 500 → Total = 60 000 XAF ✓

Règles métier

  • Aucun coefficient saisi ce mois → tous à n = 1.
  • Aucune facture saisie pour un type → brouillon reconduit du mois précédent (non publié), notifié à l'Admin pour validation (cf. §0.2).
  • Alerte (push + SMS + email selon préférences) au locataire en défaut, au Bailleur et à l'Admin J-2 avant l'échéance, puis J0 si non réglé, puis rappels J+3 / J+7.
  • Bailleur : vue complète (par locataire, total par type, historique, export). Locataire : ses propres factures uniquement.
  • Gestion du départ en cours de mois : un locataire désactivé est exclu du calcul des factures non publiées ; les factures publiées restent figées.

5.8 Signal de détresse REVU §0.2

  • Déclenchement : 5 clics rapides sur le bouton « Détresse » (anti-accident) + confirmation optionnelle de géoloc (consentement explicite).
  • Diffusion push + SMS à tous les utilisateurs actifs en temps réel ; historisé dans distress_signals.
  • Anti-abus (sans couper la sécurité) : au-delà d'un seuil (ex. 3 signaux / 3 jours), le compte passe en distress_review → l'Admin est alerté pour arbitrage ; le signal continue de partir, mais marqué « à vérifier ».
  • L'Admin peut bannir/réactiver manuellement (distress_disabled) — action journalisée (audit).
  • Suivi de résolution : un signal peut être marqué resolved par l'Admin.

5.9 Tableau d'informations (posts images)

  • Image obligatoire (JPEG/PNG, ≤ 5 Mo, Cloudinary, compression auto). Titre ≤ 100, description ≤ 300 caractères.
  • Fil commun trié par date décroissante ; l'Admin peut masquer tout post inapproprié (is_hidden).

5.10 Projet commun & cotisations cotisation

L'Admin crée/publie un projet visible par les rôles sélectionnés. Champs : Titre, image de profil, Description, Objectifs (liste), Vision, Besoins financiers, Montant de contribution/personne, Rôles destinataires (multi-select).

  • Suivi de cagnotte : table projet_contributions + barre de progression (collecté / objectif), liée aux paiements.

5.11 Prédiction / estimation de charge FIX-5

L'Admin saisit les paramètres ; le système calcule l'estimation du mois suivant, par type de charge, publiée à tous pour anticipation.

Électricité :   Montant = (I × P) + TVA + LC + T
I = différence d'indices (kWh = index_fin − index_début) · P = prix du kWh · TVA · LC = location compteur · T = transport

Eau :   Montant = (I_eau × P_eau) + frais_fixes   (formule propre, paramétrable par type)

Stocké dans predictions_facture avec montant_reel renseigné a posteriori pour comparer estimé vs réel et affiner.

5.12 Maintenance & tickets NEW

Distinct du signal de détresse : signalement non urgent (plomberie, électricité, mobilier…). Catégorie, description, photo, statut (ouvert → en cours → résolu), priorité, assignation. Notifications à chaque changement de statut. Utile au quotidien d'une cité.

5.13 Sondages & votes NEW

Décisions communautaires rapides (ex. date d'un événement, choix d'un prestataire). Question + options, un vote par utilisateur, résultats en temps réel, clôture par l'Admin.

5.14 Annuaire des résidents NEW

Vue dérivée des portfolios : recherche par compétence/diplôme, filtre « disponible aux recommandations ». Renforce le réseautage (objectif communautaire).

5.15 Documents & règlement intérieur NEW

Espace de documents partagés (règlement, PV de réunion, formulaires), visibilité par rôle, versionné, téléchargeable hors-ligne (cache PWA).

7. PWA, offline-first & internationalisation

7.1 Progressive Web App

  • next-pwa (Workbox) ; manifest.json : nom, icônes 192/512, thème #1A3C6E, display: standalone.
  • Offline-first : précache du shell ; StaleWhileRevalidate pour les listes, NetworkFirst pour les données fraîches, CacheFirst pour images/documents.
  • File de synchronisation (Background Sync / IndexedDB) : les actions hors-ligne (paiement saisi, suggestion, ticket) sont mises en file et rejouées au retour réseau.
  • Économie de data : images servies en WebP/AVIF responsives, lazy-loading, pagination serveur partout.
  • Prompt d'installation A2HS après 2 visites ; badge de notifications non lues (Badging API).
  • Push via Web Push + VAPID, abonnement en push_subscription.
Limite iOS

Le Web Push iOS ne fonctionne que sur iOS 16.4+ et uniquement si la PWA est installée (A2HS). Fallback SMS prévu pour les alertes critiques sur iPhone non installé.

7.2 Internationalisation (FR / EN / DE)

  • next-intl, fichiers /messages/{fr,en,de}.json ; détection auto à la 1re visite, surchargeable et persistée (users.language).
  • Tout est traduit : UI, erreurs, notifications, SMS, emails (selon langue du destinataire).
  • Formats date/nombre/monnaie (XAF) par locale.
  • DE optionnel (cf. §0.3) : structure prête, activation selon le public réel.

9. Sécurité & bonnes pratiques

DomaineMesure
AuthentificationJWT HS256 access 15 min + refresh 7 j (HttpOnly, SameSite=Strict), rotation & révocation par token_version. 2FA TOTP admin.
Mots de passe≥ 8 caractères + bcrypt(12). Changement forcé à la 1re connexion. Verrouillage temporaire après échecs.
Rate limiting/auth/login : 10 essais / 15 min / IP + backoff par compte. Throttle global sur l'API.
ValidationZod sur 100% des entrées (schemas partagés front/back). Aucune donnée non validée persistée.
Injection SQLPrisma paramétré ; $queryRaw tagué uniquement pour rapports, jamais d'interpolation brute.
AutorisationroleGuard + vérification d'ownership (un locataire n'accède qu'à ses ressources). Tests d'accès systématiques.
UploadMIME + taille (≤ 5 Mo) vérifiés côté serveur, ré-encodage image, pas d'exécutable. URLs signées.
TransportHTTPS obligatoire (Let's Encrypt), HSTS. CORS en liste blanche explicite.
En-têtesCSP stricte (anti-XSS), X-Frame-Options, Referrer-Policy, Permissions-Policy (géoloc).
Secrets.env non versionné : JWT_SECRET, DB_URL, VAPID, SMTP, SMS, Cloudinary, MoMo.
Données persoGéoloc & anniversaire en opt-in ; minimisation ; pas de PII dans les logs.
Auditaudit_logs sur actions sensibles (user, action, ressource, IP, UA, timestamp).
ObservabilitéSentry (erreurs), pino structuré + rotation, health checks /api/health.
Sauvegardespg_dump quotidien chiffré → stockage objet (R2/S3), restauration testée.

11.2 Étapes (production)

  1. Provisionner VPS Ubuntu 22.04 LTS : SSH durci, ufw, fail2ban, mises à jour auto.
  2. Installer Docker + Compose ; cloner le repo.
  3. Configurer .env (DB, JWT, VAPID, SMTP, SMS, Cloudinary, MoMo).
  4. docker-compose up -d (web + postgres + redis + nginx).
  5. npx prisma migrate deploy puis npx prisma db seed (admin idempotent — upsert).
  6. Nginx + SSL Let's Encrypt (certbot --nginx), HSTS.
  7. Workers BullMQ + CRON système (échéances J-2/J0/J+n, anniversaires J-7, reconductions).
  8. Test du flux complet : login admin → 2FA → user → facture → publication → paiement (MoMo) → reçu → push/SMS.
  9. Sauvegardes pg_dump chiffrées → R2/S3 ; test de restauration.
  10. GitHub Actions : lint + typecheck + tests + build + déploiement sur main.
